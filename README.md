## Встановлення

Потрібен [uv](https://docs.astral.sh/uv/).

Ініціалізація віртуального середовища
```bash
uv sync

```

# Reflection

**1. Який feature з pipeline найдорожчий у обчисленні за EXPLAIN ANALYZE? Чому: JOIN, GROUP BY, window function, Sort або Hash Aggregate?**

За планом EXPLAIN ANALYZE найбільш витратною виглядає гілка avg_order_value_30d: її WindowAgg завершується приблизно на 1284 мс, а попередній Sort використовує external merge із записом 9448 кБ на диск. Також виконується Incremental Sort. Досить дорогою є й preferred_category: для неї потрібні JOIN трьох таблиць, GroupAggregate, сортування та WindowAgg (до 883 мс). У RFM і cancellation_rate видно HashAggregate з 21 batch і використанням диска — це ознака нестачі пам’яті для агрегування. Часи вузлів вкладені, тому не є незалежними витратами кожного feature. Тимчасові файли показують, що пам’ять сильно завантажується, коли база виконує складні запити.

**2. Чи варто кешувати цей feature через Materialized View? Який refresh-cycle ви б обрали: щогодини, щодоби, on-demand?**

Так. Повний pipeline обробив 99 441 рядок за 3322,886 мс, тоді як точковий lookup із MV повернув один рядок за 0,115 мс. План lookup містить Index Only Scan по клієнтах та Index Scan за унікальним індексом MV, без повторних агрегувань. Операції тут різні за обсягом, тому час виконання не можна прямо порівнювати для тих самих запитів. Я обрав би щоденний REFRESH CONCURRENTLY: ознаки оновлюватимуться регулярно, а читання залишатиметься доступним.

**3. У якому use case звичайний VIEW був би правильнішим вибором, ніж MV?**

Для простих запитів до поточних статусів замовлень, де важливі актуальні дані одразу після зміни, а повторне обчислення недороге.

**4. Як recursive CTE забезпечує termination? Що станеться, якщо referral graph містить цикл A → B → A?**

Anchor знаходить корені через NOT EXISTS. Рекурсивна частина запам’ятовує path_ids, відхиляє вже відвідані вузли та обмежує depth < 50. Тому перехід A → B → A не повториться нескінченно; цикл без доступного кореня взагалі не потрапить до обходу.

**5. Який trade-off важливіший у цьому pipeline: freshness, latency, recompute-cost чи storage-cost?**

Головне тут — знайти той самий баланс між затримкою і тим, наскільки все свіже. MV допомагає читати швидше, але поки йде оновлення, дані вже можуть бути неактуальними. Recompute-cost і додаткове місце зберігання також мають значення, проте для пакетного ML щоденне оновлення є прийнятним компромісом.
